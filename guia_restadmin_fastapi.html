    1APIs y HTTP en lo mínimo

    FastAPI sirve para construir APIs. Antes de verlo, conviene tener claro qué es una API y cómo se habla con ella.

    Tu propio proyecto da la mejor analogía. En un restaurante, el cliente no entra a la cocina: le dice al mesero qué quiere, el mesero lleva la comanda, la cocina prepara y el mesero vuelve con el plato. Una API es ese mesero entre dos programas: una aplicación (el cliente: una app móvil, una página web, Postman) le pide algo a otra (el servidor, tu RestAdmin) siguiendo reglas fijas, sin necesidad de conocer cómo funciona por dentro.

    REST es un estilo para diseñar esas reglas sobre HTTP, el mismo protocolo que usa el navegador. Cada pedido (una petición o request) tiene cuatro partes:

    Los códigos de estado que aparecen en tu proyecto

    El código es un número de tres cifras que resume cómo salió la petición. Los 2xx son éxito, los 4xx son errores del cliente (pidió algo mal) y los 5xx son errores del servidor (el programa falló).

    204 No ContentSalió bien, pero no hay nada que devolver.DELETE exitoso (README).

    Diferencia que suelen preguntar: 400 contra 422

    422: el dato está mal formado (un texto donde va un número, un precio negativo). Lo detecta Pydantic antes de que tu código corra. 400: el dato está bien formado, pero el negocio no lo permite (el número 5 es válido, pero ya existe una mesa 5). Lo detecta tu capa de servicios.

    2Qué es FastAPI

    El framework con el que está hecho el proyecto, y la idea de async/await que aparece en casi todos los archivos.

    FastAPI es un framework de Python para construir APIs. Un framework es un conjunto de herramientas que ya resuelve lo repetitivo (recibir peticiones HTTP, leer el JSON, validar, responder) para que tú escribas solo la lógica de tu aplicación. Tiene tres rasgos que lo distinguen:

    • Usa las anotaciones de tipo de Python. Cuando escribes cantidad: int, FastAPI (a través de Pydantic) lo usa para validar el dato que llega, convertirlo y documentarlo. Por eso tu proyecto está lleno de : int, -> Mesa, str | None: no son decoración.
    • Es asíncrono. Puede atender muchas peticiones a la vez sin quedarse bloqueado esperando a la base de datos (abajo se explica).
    • Genera documentación sola. Al correr la app, en http://127.0.0.1:8000/docs aparece una página (Swagger UI) donde se ven y se prueban los endpoints.

    async y await en cinco minutos

    Piensa en un mesero que lleva una comanda a la cocina. Un mesero síncrono se queda parado en la puerta de la cocina hasta que el plato esté listo; mientras tanto nadie más es atendido. Un mesero asíncrono deja la comanda, va a atender otras mesas y vuelve cuando el plato está listo.

    En el programa, «esperar a la cocina» es esperar a la base de datos o a la red. Con async, mientras una consulta viaja a la base de datos, el servidor atiende otras peticiones.

    PalabraQué significaEn tu código
    async defDefine una corrutina: una función que puede pausarse a mitad de camino. Llamarla no la ejecuta, devuelve algo que hay que esperar.Todos los métodos de repositorios y servicios.
    await«Pausa aquí hasta que esto termine y dame el resultado». Solo se puede usar dentro de un async def.await self.session.commit(), await self.mesa_repo.get_by_id(...)
    asyncio.run(...)Arranca el ciclo de eventos y ejecuta una corrutina desde código normal (fuera de FastAPI).Final de main.py, para la prueba por consola.
    async withUn with cuya entrada y salida también se esperan (abrir y cerrar una sesión de BD).database.py: async with async_session_maker() as session
    El error clásico: olvidar el await

    Si escribes mesa = self.mesa_repo.get_by_id(5) sin await, mesa no es una Mesa: es un objeto coroutine sin ejecutar. Python además avisa «coroutine was never awaited». Regla práctica: si el método que llamas es async def, va con await.

    Por eso la cadena completa es asíncrona: el servicio hace await al repositorio, el repositorio hace await a la sesión, la sesión espera a la base de datos. Si un eslabón fuera síncrono, bloquearía todo el servidor.

    3El entorno virtual herramienta

    Lo primero que se hace al abrir el proyecto, antes de escribir una línea.

    Cuando instalas una librería con pip sin más, queda instalada en el Python de todo tu computador. El problema aparece con el segundo proyecto: este usa FastAPI 0.115 y otro de hace un año necesita una versión vieja. No pueden convivir dos versiones de la misma librería en el mismo Python.

    Un entorno virtual es una carpeta (en tu proyecto, venv/ o .venv/) con una copia aislada de Python y su propio espacio de librerías.     Convierten una carpeta en un paquete de Python, es decir, algo importable.     7El ORM y la capa de modelos models

    Cómo una clase de Python se convierte en una tabla, y por qué cada entidad tiene cinco clases.

    Qué es un ORM

    Una base de datos relacional guarda tablas con filas y columnas, y se le habla en SQL. Tu programa trabaja con clases y objetos. Un ORM (Object-Relational Mapping, mapeo objeto-relacional) traduce entre los dos mundos:

    Base de datosPython con ORMEn tu proyecto
    TablaClasetabla mesas ↔ clase Mesa
    ColumnaAtributocolumna numero ↔ mesa.numero
    FilaObjeto (instancia)la mesa 5 ↔ Mesa(numero=5, capacidad=4)
    Clave foráneaAtributo + relaciónpedido.id_mesa y pedido.mesa
    SELECT ... WHEREselect(...).where(...)select(Mesa).where(Mesa.numero == 5)

    La ventaja: escribes Python con autocompletado y tipos, el ORM genera el SQL, y cambiar de SQLite a PostgreSQL no obliga a reescribir consultas.

    Tu proyecto usa SQLModel, que une dos librerías: SQLAlchemy (el ORM de verdad, el que habla con la base) y Pydantic (la validación). Gracias a eso, una misma familia de clases sirve como tabla y como esquema de validación para la API.

    Relaciones entre tablas

    El diagrama entidad-relación de tu README, con lo que significa cada línea:

    Una relación se escribe en dos niveles:

    1. La clave foránea (columna real en la base): id_mesa: int = Field(foreign_key="mesas.id"). Se pone en el lado «muchos», porque cada pedido apunta a una mesa.
    2. El Relationship (atajo de Python, no es columna): permite escribir pedido.mesa para obtener el objeto Mesa, o mesa.pedidos para la lista. back_populates conecta los dos lados: Mesa.pedidos dice back_populates="mesa" y Pedido.mesa dice back_populates="pedidos".

    Regla para leerlas: el lado uno tiene una list[...] (una mesa tiene muchos pedidos); el lado muchos tiene un Optional[...] (un pedido tiene una sola mesa).

    Qué pasa al borrar: RESTRICT y CASCADE

    ondelete="RESTRICT"

    «No me borres si alguien me apunta». Lo usan Pedido.id_mesa y DetallePedido.id_plato: no se puede borrar una mesa con pedidos ni un plato que ya se vendió, porque se perdería el historial de ventas.

    Del lado del ORM va con passive_deletes="all" en Mesa.pedidos y Plato.detalles: «ORM, no toques a los hijos; deja que la base decida».

    ondelete="CASCADE"

    «Si borran al padre, bórrenme también». Lo usa DetallePedido.id_pedido: un detalle no tiene sentido sin su pedido.

    Del lado del ORM va con cascade_delete=True en Pedido.detalles, para que el ORM también borre los detalles que tenga cargados.

    Resumen: RESTRICT protege el historial; CASCADE limpia lo que depende totalmente del padre.
    Observación: SQLite y las claves foráneas

    SQLite, por defecto, no hace cumplir las claves foráneas a menos que se active con PRAGMA foreign_keys=ON, y database.py no lo activa. Lo probé: con SQLite, borrar un plato que está en un pedido funciona sin error y el detalle queda apuntando a un plato que ya no existe. Por eso es valioso que los servicios validen las reglas por su cuenta (como hace MesaService.delete), en vez de confiar solo en la base. En PostgreSQL el RESTRICT sí se cumple, y el borrado fallaría con IntegrityError (un 500).

    TYPE_CHECKING y las comillas en los tipos

    mesa.py necesita mencionar Pedido y pedido.py necesita mencionar Mesa. Si se importaran mutuamente de forma normal, se crearía un import circular (cada uno espera a que el otro termine de cargar). La solución tiene dos partes:

    • if TYPE_CHECKING: es False cuando el programa corre y True solo para el editor y los analizadores de tipos. El import existe para el autocompletado, pero no se ejecuta.
    • Los tipos van entre comillas, list["Pedido"]: es una referencia adelantada. SQLAlchemy resuelve el nombre después, cuando ya están cargadas todas las clases.

    8La capa de repositorios repositories

    La única capa que habla con la base de datos. Aquí están los métodos especiales, así que vale la pena ir despacio.

    Un repositorio es una clase que esconde los detalles de la base de datos detrás de métodos con nombres claros. El servicio no escribe select(Mesa).where(Mesa.numero == 5): llama mesa_repo.get_by_numero(5). Si mañana cambia la forma de consultar, solo se toca el repositorio.

    El docstring de tu BaseRepository deja escritas sus tres reglas. Apréndelas tal cual, porque son la diferencia con los servicios:

    Recibe la sesión
    La AsyncSession llega por el constructor. El repositorio no crea su propia conexión (no importa core).
    No conoce HTTP
    Nunca lanza HTTPException. Si no encuentra algo, devuelve None o una lista vacía [], y que otro decida si eso es un error.
    Devuelve tablas
    Retorna objetos de tabla (Mesa, Plato...), nunca DTOs *Public.

    1. Los tres huecos de tipo: el modelo de tabla, el DTO de creación y el DTO de actualización.

    2. El constructor guarda dos cosas: qué tabla maneja (self.model, por ejemplo la clase Mesa) y con qué sesión trabaja. Los hijos llaman a este constructor con super().__init__(Mesa, session).

    3. get_by_id: búsqueda por clave primaria con session.get. Devuelve el objeto o None; nunca lanza 404.

    4. get_multi: lista paginada ordenada por id. self.model hace que sirva para cualquier tabla. El * en los parámetros obliga a pasar skip y limit por nombre (get_multi(skip=0, limit=10)), nunca por posición.

    5. create: self.model.model_validate(obj_in) convierte el DTO de entrada (MesaCreate) en un objeto de tabla (Mesa) validándolo. Luego el trío add, commit, refresh. Devuelve el objeto ya con id.

    6. update: el corazón del PATCH. model_dump(exclude_unset=True) convierte el DTO en diccionario solo con los campos que el cliente envió. Luego setattr(db_obj, campo, valor) copia cada uno al objeto (es como escribir db_obj.capacidad = 6 cuando el nombre del campo está en una variable).

    7. Actualiza la marca de última modificación. hasattr comprueba que el modelo tenga ese campo, para que la base siga siendo genérica.

    8. Guarda y devuelve el objeto actualizado.

    9. delete: recibe el objeto, no el id. Buscarlo primero es trabajo del servicio. Es un borrado físico: la fila desaparece.

    Por qué exclude_unset=True es tan importante

    Si el cliente envía PATCH {"capacidad": 6}, el DTO MesaUpdate queda con numero=None, ubicacion=None, estado=None y capacidad=6. Sin el parámetro, model_dump() devuelve los cuatro y el for pondría None en el número, la ubicación y el estado de la mesa. Con exclude_unset=True devuelve solo {"capacidad": 6}. Lo verifiqué con tu modelo:

    >>> u = MesaUpdate(capacidad=6) >>> u.model_dump() {'numero': None, 'capacidad': 6, 'ubicacion': None, 'estado': None} >>> u.model_dump(exclude_unset=True) {'capacidad': 6}

    9La capa de servicios services

    Donde viven las reglas del restaurante. Recibe repositorios, decide si algo se puede hacer y responde con errores HTTP cuando no.

    Un servicio coordina el trabajo de uno o varios repositorios para cumplir un caso del negocio. El repositorio sabe cómo guardar un detalle; el servicio sabe cuándo se puede: el pedido debe existir y no estar pagado ni cancelado, el plato debe existir y estar disponible, el precio se copia del menú y al final hay que recalcular el total.

    Recibe repositorios
    Por el constructor, ya creados. No crea sesiones ni repositorios (eso se llama inyección de dependencias; por ahora la hace main.py a mano).
    Aplica reglas
    Valida existencia, unicidad y estados antes de escribir.
    Habla HTTP
    Lanza HTTPException con 404 o 400. Es la capa que traduce «el repositorio devolvió None» a «404 Not Found».
    No toca la sesión
    Nunca escribe select ni commit: siempre pasa por un repositorio.

    Los tres patrones que se repiten

    1. Buscar o lanzar 404

    Cada servicio tiene un get_by_id que llama al repositorio y, si devuelve None, lanza 404. Los demás métodos lo reutilizan: update y delete empiezan con await self.get_by_id(...), así el 404 está escrito en un solo lugar.

    2. Validar antes de escribir

    Primero se revisan las reglas y, solo si todas pasan, se llama al repositorio para escribir. Un raise corta la función en seco: lo que viene después no se ejecuta.

    3. Coordinar varios repositorios

    Algunos servicios necesitan repositorios de otras entidades. Quién usa a quién:

    • MesaService usa PedidoRepository para saber si una mesa tiene pedidos antes de borrarla.
    • PlatoService solo usa su repositorio: un plato no depende de nadie para crearse.
    • PedidoService usa MesaRepository para comprobar que la mesa exista.
    • DetallePedidoService usa tres: el suyo, PedidoRepository (validar el pedido y recalcular el total) y PlatoRepository (validar el plato y leer su precio).

    11El flujo de la información

    Qué viaja entre las capas, de ida y de vuelta, y un simulador paso a paso como prueba de escritorio.

    El viaje de ida y vuelta

    Cada capa recibe una cosa y entrega otra. Arriba va la ida; abajo, la vuelta.

    Tres ideas para retener del diagrama:

    • El DTO entra por arriba y se convierte en objeto de tabla dentro del repositorio (model_validate).
    • El repositorio devuelve None cuando no encuentra algo; el servicio es quien lo convierte en 404.

    12Parecidos pero distintos
    
  
    Pares que se confunden fácil y que se prestan para preguntas de selección.
    

  
    Modelo de tabla y DTO
    
  
    
    
    Mesa (table=True)
    Es una tabla real. Tiene id, fechas y relaciones. La usan los repositorios para leer y escribir. Su constructor no valida.
    
    
    MesaCreate, MesaUpdate, MesaPublic
    No son tablas. Describen lo que entra o sale por la API. Validan al crearse.
    
  
    
  
    Create y Update
    
  
    
    
    MesaCreate
    Hereda de MesaBase: los campos obligatorios siguen siéndolo. Para POST y PUT (enviar todo).
    
    
    MesaUpdate
    Hereda de SQLModel: todo opcional con None. Para PATCH (enviar solo lo que cambia) junto con exclude_unset=True.
    
  
    
  
    Repositorio y servicio
    
  
    
    
    Repositorio
    Recibe la sesión. Hace consultas (select, commit). Devuelve objetos, listas o None. No conoce HTTP.
    
    
    Servicio
    Recibe repositorios. Aplica reglas. Devuelve objetos o lanza HTTPException. Nunca toca la sesión.
    
  
    
  
    get_by_id del repositorio y del servicio
    
  
    
    
    mesa_repo.get_by_id(5)
    Devuelve Mesa | None. Si no existe, devuelve None sin quejarse.
    
    
    mesa_service.get_by_id(5)
    Devuelve Mesa (nunca None). Si no existe, lanza 404. Por eso su tipo de retorno es -> Mesa y no -> Mesa | None.
    
  
    
  
    add, commit y refresh
    
  
    
    
    session.add(obj)
    Solo anota en memoria que hay algo por guardar. Sin await. Si no hay commit, no queda nada en la base.
    
    
    await session.commit()
    Envía todo a la base y lo hace permanente.
    
    
    await session.refresh(obj) va después: relee el objeto desde la base para traer el id generado y los valores definitivos.
    
  
    
  
    Formas de leer un resultado
    
  
    
    
    result.scalars().all()
    Lista de objetos, vacía si no hay. Para listados.
    
    
    result.scalar_one_or_none()
    Un objeto o None. Para búsquedas por un campo único. Falla si hay más de uno.
    
    
    result.scalar_one() exige exactamente un resultado (lo usa update_total). session.get(Modelo, id) busca por clave primaria sin escribir select.
    
  
    
  
    model_validate y model_dump
    
  
    
    
    Mesa.model_validate(dto)
    De DTO (u otro objeto o diccionario) a objeto de tabla, validando. Se usa al crear. Acepta update={...} para agregar campos.
    
    
    dto.model_dump(exclude_unset=True)
    De objeto a diccionario. Se usa al actualizar para recorrer solo los campos enviados.
    
  
    
  
    cascade_delete y passive_deletes
    
  
    
    
    cascade_delete=True
    En Pedido.detalles. El ORM borra los hijos junto con el padre. Va con ondelete="CASCADE".
    
    
    passive_deletes="all"
    En Mesa.pedidos y Plato.detalles. El ORM no toca a los hijos y deja decidir a la base. Va con ondelete="RESTRICT".
    
  
    
  
    Método heredado y sobrescrito
    
  
    
    
    Heredado
    MesaRepository.update: no está escrito en mesa.py, se usa el de BaseRepository.
    
    
    Sobrescrito
    DetallePedidoRepository.update: mismo nombre, reescrito en el hijo para recalcular el subtotal. Para ese repositorio, el de la base ya no se usa.
    
  
    
  
    create y create_for_pedido
    
  
    
    
    BaseRepository.create(obj_in)
    Solo recibe el DTO. Sirve cuando el DTO trae todo lo necesario (mesa, plato, pedido).
    
    
    create_for_pedido(pedido_id=, detalle_in=, precio_unitario=)
    Recibe el DTO más lo que el cliente no envía. Calcula el subtotal.
    
  
    
  
    Engine y sesión
    
  
    
    
    Engine
    Uno para toda la app (database.py). Sabe la URL y maneja el pool de conexiones.
    
    
    AsyncSession
    Una por petición o prueba. Es la que reciben los repositorios.
    
  
    
  
    Entorno virtual y requirements.txt
    
  
    
    
    .venv/
    La carpeta con Python y las librerías instaladas. Local, no se sube.
    
    
    requirements.txt
    La lista de librerías. Se sube, para que otros recreen el entorno con pip install -r.
    
    
    Lo mismo pasa con .env (valores reales, no se sube) y .env.example (plantilla, sí se sube).
    
  
    
  
    PUT y PATCH
    
  
    
    
    PUT
    Reemplaza todo el recurso. Usa el DTO *Create (campos obligatorios).
    
    
    PATCH
    Cambia solo lo enviado. Usa el DTO *Update (todo opcional).
